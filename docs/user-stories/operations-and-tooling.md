# 配置、运行与贡献者工具

## K. 配置、运行与服务管理

| 编号 / 功能               | User story                                                                                            | 验收要点                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| ------------------------- | ----------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| US-K01 单二进制运行       | 作为部署者，我希望下载一个匹配平台的二进制就能前台运行，以便减少安装成本。                            | 支持 Linux/macOS、amd64/arm64；浏览器资源内嵌，运行端无需 Node、Go、tmux 或数据库；`webmux` 与 `webmux serve` 均可启动；`--log-file` 以 0600 文件保存 stdout/stderr，旧文件保留为 `.1`，启动方关闭管道后仍可运行。                                                                                                                                                                                                                                                                 |
| US-K02 初始化私有配置     | 作为部署者，我希望自动生成带随机 token 的配置，以便快速准备自己的服务。                               | `config init` 使用模板与随机 token 创建私有目录和 0600 文件，不向输出打印 token；默认拒绝覆盖，显式 `--force` 时原文件保留为 `.bak`；支持 `--listen` 和配置路径；`config path` 可显示存在状态或 JSON；未显式 `--config` 且默认文件缺失时，首次 `serve` 使用同一模板与 token 生成逻辑自动创建，启动输出说明创建/使用的路径并提示用 `webmux status --json --reveal-token` 查看 token；并发首次启动通过原子发布只创建一个文件，已有文件不重写；`service install` 与托盘复用同一逻辑。 |
| US-K03 检查与覆盖配置     | 作为部署者，我希望启动前检查配置并用命令行覆盖地址或 token，以便发现配置错误和临时调整运行环境。      | `config check`/`validate` 校验而不启动服务，TOML 语法错误带行列号，可输出 JSON；`config show` 查看生效配置且不含 token；显式指定缺失文件时报错且不会创建，默认文件缺失时 `config show`/`validate` 仍按默认值工作，只有 `serve` 会自动生成；`--listen`、`--token` 优先且只覆盖本次进程，显式空 token 也能覆盖（非 loopback 地址仍自动生成 token，见 US-A03）；配置修改需重启生效。                                                                                                  |
| US-K04 调整会话与提醒行为 | 作为部署者，我希望配置默认目录、缓冲和状态判断，并单独管理启动命令，以便适配自己的 agent 与资源预算。 | 支持 `default_cwd`、`scrollback_bytes`、`idle_after_seconds`、`prompt_patterns`、`agent_protocol`、`bell_attention`、`program_status`，校验正则；启动命令完全通过自定义配置或显式 argv 提供，原 `shell`/`presets` 配置项不再提供内置命令，新安装首次启动在 `launch-configs.json` 写入常见 agent 预设；提醒集成方式见 [使用指南](../usage.md#需要你介入的提醒)。                                                                                                                    |
| US-K05 安装后台用户服务   | 作为部署者，我希望以当前用户安装并启动后台服务，以便不需要一直开着前台终端。                          | `service install` 使用 Linux systemd 用户服务或 macOS LaunchAgent，无需 sudo；引用二进制和配置的绝对路径；默认配置缺失时与首次 `serve` 共用生成逻辑，创建后重新读取并校验，显式配置必须已存在且有效；保留必要 PATH 与运行环境。                                                                                                                                                                                                                                                    |
| US-K06 预览与更新服务定义 | 作为部署者，我希望先预览服务定义，并明确覆盖旧定义，以便检查安装位置与启动参数。                      | `service install --dry-run` 只打印定义，不写文件或创建配置；定义输出失败时返回错误；已有定义须 `--force` 替换并重启；二进制移动后可重新安装更新路径。                                                                                                                                                                                                                                                                                                                              |
| US-K07 启停、诊断与卸载   | 作为部署者，我希望用统一命令管理后台服务并查看日志，以便维护和排查故障。                              | 提供 start、stop、restart、status、logs、logs --follow/-f、uninstall；停止、重启、卸载会结束会话；卸载保留二进制、配置、日志与状态目录；服务启用不等于端口已监听，应结合状态和日志诊断。                                                                                                                                                                                                                                                                                           |
| US-K08 保存仓库清单       | 作为部署者，我希望指定状态目录并保护其内容，以便重启或升级后仍保留项目登记。                          | `state_dir` 保存仓库清单、受保护的运行时记录/本机 API 信息及可选 cloudflared 缓存，不持久保存会话或终端输出；支持 XDG 默认路径；仓库清单使用私有权限、原子更新与单实例锁；仓库存储失败不阻止直接终端工作；推送订阅保存或删除失败返回固定 500 文案，并在服务日志记录底层存储原因，日志和响应不包含订阅 endpoint 或密钥。                                                                                                                                                            |
| US-K09 可信远程入口与升级 | 作为部署者，我希望通过可信 VPN 或 HTTPS 代理访问，并知道升级的影响，以便维护远程终端。                | `listen`、`token`、`allowed_origins` 配合部署；TLS 由外部代理提供，正确保留 Host 并配置 Origin；`version` 与 `help` 提供版本和命令信息，`version --json` 另含控制契约版本且不读取配置；替换二进制后需重启，重启结束会话但保留仓库登记与磁盘工作树。                                                                                                                                                                                                                                |
| US-K10 定位设置分区       | 作为使用者，我希望通过分区导航快速找到设置项，以便在桌面和手机上减少长页面翻找。                      | 桌面左侧显示固定分区导航，手机顶部显示可横向滚动的吸顶导航；提供快捷指令、启动配置、草稿与暂存、公网访问、Tailscale、通知推送、输出预览七个入口；点击或键盘激活滚动到对应分区并转移焦点，滚动时高亮当前分区；支持地址片段直达和浏览器前进后退；定位不卸载表单、不丢失尚未保存的输入。                                                                                                                                                                                              |

## L. 开发、验证与发布支持

本节描述贡献者使用的工程能力，不增加面向终端使用者的产品承诺。

| 编号 / 功能                 | User story                                                                                                                                              | 验收要点                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| US-L01 本地开发与构建       | 作为贡献者，我希望使用统一命令安装锁定依赖、运行前端和构建内嵌程序，以便复现开发与发布环境。                                                            | 本地与 CI 使用 `.nvmrc` 固定的 Node.js 26.12.1；本地通过官方独立脚本安装 pnpm 12.11.2，CI 使用 pnpm/action-setup；使用 pnpm frozen lockfile；Vite 代理 API/WebSocket 到独立后端并需配置开发 Origin；`make web/build/install` 提供检查、打包与安装。                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| US-L02 分层验证与诊断       | 作为贡献者，我希望运行 Go race、前端单元、浏览器与隔离 E2E 测试，以便验证会话、安全和交互行为。                                                         | 提供 `make test` 与分层入口、类型/格式/lint 检查；Go 采用 Uber Style Guide 与登记的仓库例外，`make check` 和 CI 在前端构建后执行 `go vet ./...` 及固定 v2.15.0 的 golangci-lint（errcheck/govet/ineffassign/staticcheck/unused），生产零告警，测试仅冻结 errcheck，新增代码零新增告警，豁免只能收紧；CI 按冻结锁文件统一安装并打包 Playwright 运行依赖，一次构建供 Ubuntu 6 个和 macOS 3 个 E2E 分片共用；分片仅准备 Node 与浏览器，不重复安装 pnpm、前端依赖、Go 或构建应用；macOS Go race 复用同轮前端产物；显式预构建路径无效时失败，本地默认仍从源码构建；macOS 原生 Go race 与 3 个 E2E 分片独立运行；性能测试保持单 worker 和 4x CPU 节流；`Test result` 要求两个平台的全部分片及其他 job 成功；E2E 使用独立后端、目录与端口，等待隔离 Shell 提示符就绪后输入命令；失败有报告与 trace；测试不连接现有开发服务。 |
| US-L03 预览 UI 与生成证据   | 作为贡献者，我希望用真实组件预览极端内容、明暗主题和屏幕尺寸，以便发现溢出并为 UI 变更提供证据。                                                        | Storybook 提供设计系统、工作区与溢出场景；浏览器检查布局与可达性；截图脚本运行真实后端；可见 UI 的 PR 按项目要求附最终实现截图。                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| US-L04 基线评测与多平台发布 | 作为维护者，我希望可复现地测量核心能力并构建各平台产物，以便比较回归和交付版本。                                                                        | `make baseline` 使用隔离环境评估创建、输入、回放、生命周期、安全等能力，报告通过率与延迟边界；`BenchmarkAttachOutput` 用真实 PTY → Session → Attach → WebSocket 测量连续输出、控制边界及大块输出的分配，并校验字节与顺序；`make release` 禁用 CGO，构建 Linux/macOS 服务及 Windows CLI/托盘双架构产物，嵌入服务摘要并生成 SHA256SUMS；`make tray` 可单独构建托盘；现有 CI 执行相应质量检查。                                                                                                                                                                                                                                                                                                                                                                                                                          |
| US-L05 分层架构约束         | 作为贡献者，我希望 Controller 与 Service 的边界和线上 JSON 形状由测试守住，以便越界依赖或协议漂移在 `go test` 中就被发现，而不是靠评审。                | `go test ./...` 包含 `internal/archtest`：未归类或失效的包、越界依赖、Controller 直接 I/O 或使用未登记的 Service 包级函数、Service 携带 HTTP 状态、编解码非 `contract` 类型等违规一次列出位置、R0–R10 编号及修复提示。纯函数例外需理由且仍被使用；允许业务整数与非错误对象的领域 Status。R9 检查包级初始化及编码器函数值/方法值，登记函数不能借别名绕过。固定样例覆盖违规与合规写法。95 份线上快照分六组独立运行，仅归一化明确动态字段，业务正文、确定性 Git OID、摘要和固定输入保留；差异可见，有意变更用 `-update` 重新录制；必填响应数组/映射即使服务值为 nil 也编码为 `[]`/`{}`，nullable 字段保留 `null`，独立 Go 数组 fixture 经前端 Zod 解析验证。                                                                                                                                                             |
| US-L06 前端架构守卫         | 作为贡献者或 coding agent，我希望在提交前得到复用组件、设计令牌和分层方面的具体报错，以便新增 UI 复用设计系统，而不是重造组件或复制样式。               | `pnpm --dir web check:arch` 依次运行 ESLint（`@shadcn/lint` 与 Svelte 模板规则）、dependency-cruiser、jscpd、knip 与 Vitest 架构测试，`make check` 与 CI 的格式/构建 job 同样执行；报错说明应复用的组件、size/variant 或主题令牌；提交的基线为空，任何违规都会失败；引入带存量违规的新规则时可先记录基线，`arch:ratchet` 只删除已修复的记录；oxlint 仍是通用 lint。                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| US-L07 订阅模型辅助贡献     | 作为维护者，我希望 Pullfrog 使用自己的 OpenCode Go 订阅运行任务，以便通过指定的 DeepSeek Flash 模型辅助仓库维护。                                       | Pullfrog workflow 接收 prompt 并显式指定 `opencode-go/deepseek-v4.1-flash` 与 `effort: high`，固定 High 推理等级；使用 GitHub Actions Secret `OPENCODE_API_KEY`，不再注入 DeepSeek 直连密钥；配置说明列出 OpenCode Global 区域授权、Pullfrog BYOK 与 Custom 模型设置以及订阅额度限制。                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| US-L08 文档与 spec 治理     | 作为贡献者或 coding agent，我希望文档和 OpenSpec 规格有可执行的行数、体积与目录扇出上限，以便单次读取保持可管理，失败信息直接给出拆分、合并或整理指令。 | `make check` 与 CI 的格式/构建 job 运行 `make docs-check`，即 `go test -count=1 ./internal/docguard`；`docs/**/*.md` 与 `openspec/specs/**/spec.md` 限制为 20–400 行且不超过 48 KiB；未归档的 `openspec/changes/**/*.md` 限制为不超过 400 行且不超过 48 KiB（不设行数下限）；`openspec/changes/archive/**` 不参与体积检查；`docs/` 与 `openspec/` 的每一级直接子目录不超过 20 个，`docs/images/`、`openspec/specs/` 与 `openspec/changes/archive/` 的固定布局豁免；失败信息列出实测值、阈值与 AI 指令，要求按主题拆分或合并并保留旧路径为树状索引，规则与例外见 [文档治理](../doc-governance.md)。                                                                                                                                                                                                                    |
